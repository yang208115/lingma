# 多 Agent 编排重设计

日期：2026-11-05。状态：S1（引擎与正文）已实现，S2—S4 见 §12 与文末实施记录。取代[多 Agent 编排完善设计](./多Agent编排完善设计.md)中尚未实现的部分；已有行为见[通用编排与流程画布实施](./MA-通用编排与流程画布实施.md)。

## 1. 为什么重做

使用中暴露的问题，以及对应的设计回应：

| 问题 | 根因 | 本设计的回应 |
| --- | --- | --- |
| 看不到节点输出，没有章纲就无法给意见 | 节点是黑盒，作者只能在“确认章纲”一处介入 | 每个节点都有产物页和闸门，随时可看、可改、可写意见 |
| 模型少交一个字段，整个运行报 `INTERNAL_ERROR` | 产物是严格 JSON，靠补全循环（`artifact-repair.ts`）兜底 | 产物改为 Markdown，不再做字段补全循环 |
| `workflows/service.ts` 过千行，难定位 | 隐式依赖、系统汇总节点、反馈回路、补全、恢复都在一个类里 | 引擎只保留调度与闸门，业务适配拆出去 |
| 审校意见只能整稿“使用/不使用” | 没有逐条处理 | 意见清单逐条采纳或忽略，修订只处理被采纳的条目 |

## 2. 原则

1. 确定性调度，模型不决定流转、权限和落盘。沿用现有底线：全局模型并发 1、活跃队列容量 32、作者接受后才写入正式文档。
2. **画布保留**，作为唯一的编排配置方式。去掉旧的“阶段顺序隐式派生依赖”，依赖只来自连线。
3. 产物是 Markdown，作者可直接阅读、编辑。结构化元数据只保留引擎必需的最小集合。
4. 每个节点结束后都有作者闸门。默认自动放行，也可设为手动。
5. 不为兼容旧数据背负包袱：旧模板、运行记录整体清除（见 §9）。

## 3. 运行模型

### 3.1 节点类型

沿用画布上的节点，类型调整为：

| 类型 | 产物 | 调用模型 | 说明 |
| --- | --- | --- | --- |
| 策划 `plan` | 章纲或提纲 Markdown | 是 | 可选 |
| 生成 `generate` | 正文或记录集 Markdown | 是 | 至少一个；多个必须串成一条内容链 |
| 分析 `analysis` | 分析笔记 Markdown | 是 | 只供下游参考，不参与通过判断 |
| 审校 `review` | 意见清单 Markdown | 是 | 多个审校并行读同一稿，首轮互相不可见 |
| 汇总 `merge` | 合并后的意见清单 | **否** | 系统节点，画布上可见、不可删；汇入全部审校，去重并保留来源 |
| 修订 `revise` | 新版产物 | 是 | 只接收被采纳的意见 |

`merge` 原先是画布上“不可见的系统边界”，现在显式画出，避免作者看不懂回路。

### 3.2 依赖与回路

- 依赖只来自连线（`dependsOn`），发布时校验：节点存在、无重复连线、无自环、无环、每个审校位于最终生成节点下游、至少一个必需审校。
- 修订回路由引擎管理，不是普通连线：`merge` 之后若存在被采纳的意见且开启自动修订，进入 `revise`，随后**开启新一轮**——重新执行全部审校与 `merge`。每一轮都有轮次编号，作为所有产物的属性保存，旧轮产物保留只读。
- 新一轮开始时，只有“被替换稿件的消费者”需要重跑：审校与 `merge`。策划、分析不重跑。
- 修订产物与上一稿完全相同（字符串相等）时不再自动开启下一轮，停在闸门等待作者。这是内容无变化的判断，不是次数限制。

### 3.3 节点状态

`pending → queued → running → awaiting_gate → released`，另有 `failed`、`skipped`、`stale`（被新一轮替代）。运行状态沿用 `queued / running / awaiting_input / awaiting_acceptance / paused / completed / failed / limited / cancelled / interrupted`，其中 `awaiting_input` 的原因由结构化 `reason` 区分：`GATE`（等闸门）、`ADOPT`（等采纳意见）、`NO_CHANGE`（修订无变化）。`reason` 只用于界面展示，不是权限判断依据。

## 4. 作者闸门

每个节点有两个配置项，位于画布右侧节点配置面板：

- **放行方式**：`自动`（默认）或 `手动`。
- **运行时覆盖**：启动运行时可以把“全部手动”作为一个开关，不改模板。

产物生成后：

- 自动放行：节点标记 `released`，立即调度下游。作者事后仍可查看产物。
- 手动放行：运行进入 `awaiting_input`（`GATE`）。作者可以：
  1. 查看完整输出（见 §7）；
  2. **直接编辑产物**——产生新产物，旧产物保留，所有下游与已完成的审校标记 `stale`；
  3. 写意见，意见作为下游节点的“作者补充”输入；
  4. 放行；
  5. 重跑本节点（同输入，新尝试）。

自动放行节点也可以在运行中点“暂停”，在节点边界停下，随后同样可查看和编辑。

“定稿”不是节点，是运行的终点：最后一个生成/修订产物加上通过的审校，形成提议；**接受提议固定需要作者操作**，不受放行方式影响。

## 5. 产物契约（Markdown）

### 5.1 单产物

模型的最终输出就是产物，服务端不要求 JSON。引擎只保存：

```ts
{
  id, workflowId, nodeKey, round, attemptRunId,
  kind: 'plan' | 'draft' | 'analysis' | 'review' | 'merge' | 'records',
  markdown: string,
  contentHash: string,
  inputArtifactIds: string[],
  createdBy: 'model' | 'author' | 'system',
  supersedes: string | null
}
```

`createdBy='author'` 表示作者编辑，`supersedes` 指向被替换的产物，旧产物保留。去掉原先按 payload 类型区分的 7 种严格 schema。

### 5.2 审校意见清单

约定格式，审校 Agent 的内置提示词随之更新：

```markdown
### [P1] 一句话概括问题
> 稿件中的原句（必须原样引用）

说明与修改建议。依据：资料《xx》 / author
```

服务端按 `### [P0|P1|P2]` 逐条解析为意见条目：严重度、概括、原句、正文。解析规则宽松：

- 缺原句的条目仍保留，标记“未定位”，不丢弃。
- 完全无法解析时，整段作为一条“未结构化意见”展示给作者，由作者决定采纳或忽略。**不触发重试或补全循环。**
- 原句能在稿件中找到时记录位置，用于界面高亮；找不到只提示，不报错。

`merge` 把各审校的条目合并为一份清单：精确重复（同严重度、同原句、同概括）合并并保留来源列表；无法确定重复的分别保留。

### 5.3 多记录产物（基础信息、事件批）

`records` 类产物按约定的二级标题分条：

```markdown
## [人物] 运阳
正文……

## [故事定位] 双阳同天
正文……
```

方括号内是分类，适配器按分类把条目映射到文档类型。无标题或分类未知的内容归入“未分类”，展示给作者手动归类，**不自动补全，也不用缺失分类驱动二次模型调用**。是否覆盖了所有所选分类，由 `merge` 以外的一个轻量**覆盖检查**给出提示（非阻塞），作者可选择“针对缺失分类重跑生成节点”，由作者触发而不是引擎自动循环。

### 5.4 作者意见的作用范围

作者意见绑定到“某个节点的某个产物”，只进入该节点的直接下游输入，不无限累积进所有后续上下文。

## 6. 逐条意见处理

`merge` 之后运行停在“采纳”闸门（自动放行时默认全部 P0/P1 采纳，P2 仅展示）：

- 每条意见可切换 `采纳 / 忽略`，P0 忽略需填写理由。
- 开启自动修订：被采纳的条目交给 `revise`；没有被采纳条目则直接进入定稿。
- 关闭自动修订或没有修订节点：停在闸门，作者可直接编辑稿件后让审校重新跑一轮。
- 忽略记录保存“条目、稿件、轮次、理由、时间”，仅对当前稿件有效；新稿出现的同类问题需重新处理。

## 7. 作者界面

- **运行卡**（写作助手内）：保持简洁，只显示节点列表、状态和当前需要作者做的事。
- **节点产物页**：每个节点可打开完整输出，在大区域（编辑区标签页，沿用现有“预览标签”）里显示，支持编辑。审校节点显示意见清单与采纳开关。返回内容（思考、工具调用）通过“查看运行详情”复用 `RunDiagnostics`。
- **画布**：保留 React Flow；节点配置面板新增“放行方式”；`merge` 显示为带锁的系统节点；运行视图可在画布上高亮当前节点与各节点状态。
- 长内容一律放进限高可滚动的框或标签页，不撑开卡片。

## 8. 任务类型与适配器

引擎只负责调度与闸门；任务类型决定三件事：生成节点的输入、`records` 如何拆条、接受时如何保存。

| 任务 | 产物 | 保存 |
| --- | --- | --- |
| 正文 `chapter_write` | `draft` | 提议 → 作者接受 → 新文档版本；无目标时按标题新建章节 |
| 基础信息 `basic_information` | `records` | 按分类映射到五类要素，可单条/分类/全部采用，锁定字段与版本保护沿用现有规则 |
| 世界观 `worldbuilding` | `records` | 同上，仅世界观分类 |
| 总纲 `master_outline` | `draft` | 新建或修改总纲 |
| 事件 `story_events` | `records` | 批量新建事件，或修改单个已有事件 |

适配器接口（服务端内部）：`buildInput(task, round)`、`splitRecords(markdown)`、`validateForSave(items)`、`save(items, tx)`。保存仍在事务内完成权限、基准、引用校验，并沿用 `expectedRevision` 与 `Idempotency-Key`。

- 角色库中旧的审校提示词需随输出格式更新（§5.2）；内置角色随版本重新发布，作者自定义角色保留，但其提示词若仍要求 JSON 输出，需要作者自行改写，界面在角色页提示。

## 10. 恢复、取消与并发

沿用并简化现有机制：

- 重启不自动调用模型；作者恢复时先对账：子运行已完成且产物已提交的，认领一次后进入闸门，不重复调用。
- 取消先关闭父流程推进资格，再取消排队与进行中的请求；迟到结果只存历史，不发布给下游。
- 节点重试创建新尝试，输入相同且有完整检查点时复用。
- 同一作品同时只有一个活跃工作流持有写作占用；等待闸门、暂停、中断、可重试失败仍持有，作者可“结束并释放作品”。
- 控制、节点完成、接受按事务成功顺序裁决；重复请求靠幂等键，竞态靠 `expectedRevision`。

## 11. 引擎代码结构（拟）

把 `workflows/service.ts` 拆成职责单一的模块，`WorkflowService` 只做门面：

- `graph.ts`：依赖图校验、拓扑、轮次与失效计算（纯函数，可单测）。
- `scheduler.ts`：就绪判断、入队、暂停与取消。
- `gates.ts`：闸门、编辑产物、意见、放行。
- `reviews.ts`：意见解析、合并、采纳状态。
- `artifacts.ts`：产物读写与血缘。
- `adapters/*.ts`：§8 的各任务适配器。
- `recovery.ts`：启动对账。

删除：`artifact-repair.ts`、按 payload 区分的严格 schema 与对应补全逻辑、阶段顺序派生依赖的兼容代码。

## 13. 验收场景

| 场景 | 必须观察到的结果 |
| --- | --- |
| 模型输出任意 Markdown，没有任何约定标题 | 产物保存成功，审校清单显示一条“未结构化意见”，不报错、不重试 |
| 节点设为手动，运行到该节点 | 运行停在闸门，可看完整输出；放行前下游不启动 |
| 作者编辑生成稿 | 新产物 `createdBy='author'`，旧产物保留，已有审校与提议标记 `stale` |
| 作者忽略 P0 但未填理由 | 请求被拒绝，提示填写理由 |
| 修订返回与上一稿完全相同 | 不再开启新一轮，停在 `NO_CHANGE` 闸门 |
| 暂停与节点完成同时发生 | 不启动下游，节点产物保留；恢复后进入闸门或下一节点 |
| 取消与模型完成同时发生 | 父状态不复活，产物不传给下游，不突破并发 1 |
| 子运行完成、父状态未更新时重启 | 恢复时认领一次，不重复调用与计费 |
| 基础信息缺分类 | 给出覆盖提示；仅在作者点“重跑缺失分类”后才再调用模型 |
| 两个浏览器重复接受 | 幂等返回，正式文档最多新增一个版本 |
| 全部审校通过且自动放行 | 全流程无人值守跑到“等待接受提议”，且接受仍需作者 |
| 迁移 0020 后启动 | 角色库、模型配置、业务文档完整；内置模板重新出现 |

测试顺序：`graph.ts`/`reviews.ts` 纯函数单测 → 服务端集成测试（本地模拟模型）→ 真实 pi-ai SDK 配本地 HTTP 模拟供应商的浏览器测试。真实模型的质量、延迟与费用不在协议测试范围内。

- **测试**：`apps/server/test/workflows.test.ts` 重写为 19 条用例，覆盖无人值守流水线、审校互相独立、采纳驱动修订、忽略 P0 需理由、手动闸门与编辑、失效与新一轮、修订无变化停止、未结构化意见不重试、取消、重启中断、Markdown 分条与各任务类型保存；`e2e/workflows.spec.ts` 同步为新流程并加入手动放行路径。

与设计的差异与取舍：

- 修订回路仍由引擎按“轮次”生成节点（`name@rN`），不是普通连线；旧轮次节点保留为只读历史。
- “覆盖检查”按设计用规则实现：基础信息缺分类只给出警告（`resultWarnings`），不触发二次模型调用。
- 自定义角色里要求 JSON 输出的提示词不会自动迁移；本版内置角色与审校提示词已改为 Markdown 约定，自定义角色需作者自行改写（待确认问题 1 仍开放）。
- 严重度仍保留 P0/P1/P2 三档（待确认问题 2）。
- 自定义角色提示词中残留的 JSON/提交工具要求，角色页会提示并提供“移除旧格式要求”（待确认问题 1 的最小方案）。
