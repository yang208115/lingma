## 3. 建议的 Workspace 结构

```text
apps/
  web/                  # 小说编辑、资料、Skill 与运行界面
  server/               # HTTP、运行管理、资料访问及持久化
packages/
  agent/                # 自研 loop、模型适配与动作调度
  shared/               # 前后端共用的数据契约与事件定义
docs/
pnpm-workspace.yaml
package.json
```

第一版先使用这些边界。数据库和 Skill 管理可作为 server 内部模块，形成实际复用需求后再拆包。

建议依赖方向：web 使用 shared；server 使用 shared 和 agent；agent 仅依赖 shared 及必要的模型接入库，不依赖 web、HTTP 框架或具体数据库。

server 将作品资料读取、修改提议、运行记录等能力通过接口传给 agent。这样可以单独验证循环逻辑，也能在更换保存方式时保留 Agent 核心。

共享 TypeScript 类型之外，HTTP 输入和模型生成的动作参数仍需要运行时校验。

## 4. 自研 loop 的建议边界

| 模块       | 建议职责                                                                  |
| ---------- | ------------------------------------------------------------------------- |
| 模型适配   | 封装 pi-ai 请求与返回，暴露循环需要的文本、动作请求、结束原因、用量和错误 |
| 上下文准备 | 注入 Skill 名称/描述/版本目录与资料快照，供 Agent 用工具按需加载          |
| 循环调度   | 发起模型调用，处理响应，决定执行动作、继续下一轮或结束                    |
| 动作调度   | 校验动作名称与参数，调用注入的应用能力，把结果返回模型                    |
| 运行控制   | 管理取消、轮次与其他已确认限制                                            |
| 运行事件   | 输出轮次、文本增量、动作开始/结束、用量和最终状态                         |
| 记录接口   | 让 server 保存完整轮次与状态；具体数据库访问放在 server                   |

本次采用 D1—D3 的有限应用动作循环、作者独立确认提议、单片段/单章及可配置轮次/期限作为实施基线，详见契约文档。PRD 中主人回答保持原样；不增加外部工具、脚本执行、自动写正文或跨重启自动恢复。

### 4.1 建议的执行流程

```text
接收任务与配置
  → 固定本次 Skill 目录和资料输入，全文由 Agent 调用工具加载
  → 检查取消信号及运行限制
  → 通过 pi-ai 请求模型并发送流式事件
  → 检查完整响应及结束原因
      → 有允许的应用动作：校验、执行、记录结果，再进入下一轮
      → 无动作且正常完成：保存候选结果，结束
      → 错误、取消、截断或达到限制：保留已有结果，明确标记原因
```

若选择“写作→自查→重写”的产品模式，还需显式定义继续条件，不能假设模型在没有动作请求时会自动进入下一轮。

### 4.2 建议优先处理的边界

- 模型分片输出先作为流式事件展示，完整动作请求收到并校验后再执行。
- 区分正常完成、输出截断、失败和取消，避免把不完整正文标成已完成。
- 将取消信号传递到模型调用和应用动作；浏览器断开是否取消任务需单独定义。
- 对未知动作和无效参数返回明确结果，不执行未注册能力。
- 正文候选和资料更新提议通过应用层确认写入；如运行期间原文被编辑，需校验基准版本。
- 失败重试与恢复须区分已经完成的动作和状态不明的动作，防止重复写入。
- Token 或费用不可用时记录未知；停止前检查下一轮的限制，不承诺撤销已发生的远端费用。

这些边界已在 P00 契约中采用，默认数值以 shared schema 为准。P04 已实现循环限额、可选 Token 阈值与用量汇总；P05 已接入实际资料、运行管理与持久化。上下文采用 UTF-8 字节保守估算，留 15% 余量并预留输出，每轮复核；金额硬预算及可靠 tokenizer 未启用。模型配置只持久化环境变量或本机加密凭据引用，界面可直接填写 API 密钥；并发 1、活跃队列 32，完整实施与限制见 [P05 实施说明](./P05-写作流程实施.md)。

## 5. 后续设计顺序建议

1. 确认 PRD 中 loop 行为、数据落点和备份方式。
2. 定义运行事件、应用动作和保存接口，明确作者确认发生的位置。
3. 固定前后端框架及数据库，建立 Workspace 工程。
4. 先验证最小循环：读取一条资料 → 模型继续响应 → 产生候选文本，并覆盖取消、失败、无效动作和轮次上限。
5. 将循环接入小说编辑与 Skill 试运行，再完善历史和备份。
