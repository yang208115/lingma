## 1. 产品定义

P02 实施进度：小说工作区、文档/元数据版本、冲突处理、导入预览确认和 TXT 导出已完成；实际接口及实现限制见 [P02 实施说明](./P02-小说工作区实施.md)。P03 已补充 Skill 本地/公开 Git 导入、预览、编辑和不可变版本，细节见 [P03 实施说明](./P03-Skill管理实施.md)。P05 模型调用路径已接通；P06 的 Skill 实验案例与双版本比较仍未交付。

面向长篇连载小说作者的 Web 写作工作台，把小说资料、可编辑和试运行的 Skill、单 Agent loop 放在同一个创作环境中。作者能够查看 AI 使用的资料和写作方法，审阅产出并决定是否应用到正文或资料库。

第一版供自己及少量朋友各自独立使用，支持本机运行后通过浏览器访问，也支持部署到服务器。两种部署方式均为已确认需求；服务器部署时的数据归属和用户隔离方式尚待确定。

### 1.1 要解决的问题

| 优先顺序 | 已确认的问题     | 产品应提供的帮助                                     |
| -------- | ---------------- | ---------------------------------------------------- |
| 1        | 章节前后矛盾     | 提供相关前文和大纲，支持检查矛盾并定位依据           |
| 2        | 人物设定容易遗忘 | 集中管理人物资料，让作者确认本次使用的人物信息       |

### 1.2 第一版核心体验建议

导入前文章节 → 补充大纲和人物 → 导入写作 Skill → 提出当前章节任务 → 调整推荐上下文 → 单 Agent 执行并产生候选结果 → 作者审阅和修改 → 应用到正文 → 保存版本并导出 TXT。

其中，loop 和运行规模的当前实施基线已在 P00 记录；单章字数、上下文预算等局部待定项在相应阶段处理。

### 3.1 导入与首次写作

1. 创建作品，导入 Markdown 或 TXT。建议先预览章节拆分结果，再确认导入。
2. 编辑卷章结构、总纲、章纲和人物资料。
3. 配置供应商与模型，导入至少一个 Skill。
4. 在某章旁边提出写作或检查任务。
5. 查看自动推荐的上下文，增删资料后开始运行。
6. 审阅候选文本；建议通过明确的应用操作写入正文。

### 3.2 Skill 调整与比较

1. 打开 Skill 的格式化预览，查看关联文件和使用示例。
2. 进入编辑模式，保存一个新的工作版本。
3. 选择测试案例或当前作品的资料，分别运行修改前后版本。
4. 并排查看结果及文本差异，再决定继续调整或采用新版本。

比较时建议固定模型、参数、案例及资料版本。模型采样可能产生不同结果，界面应说明这一点；不把输出差异直接解释为质量提升。

## 6. 上下文与资料更新

### 6.1 上下文选择

已确认：系统自动推荐，作者可以调整，并能查看实际使用的资料。

建议按照当前章节、任务文本和相关人物，推荐章纲、总纲片段、人物资料及相关前文。第一版可先采用章节关系和文本检索，不强制引入向量数据库。

建议规则：

- 资料按条目列出，显示来源和版本，作者能够添加或移除。
- 明确区分已发生的前文与未来章纲；是否使用后续规划应由作者可见地控制。
- 输入超过模型限制时，提示裁剪或摘要方案；不静默丢弃作者指定资料。
- 开始任务后固定本次上下文快照；后续编辑不改变已记录的输入。
- 检查矛盾时返回相关章节或资料引用；资料不足时允许给出“依据不足”。

以上规则为建议细化。自动推荐效果需通过真实存稿试用评估，不能把未检索到的内容视为不存在。

### 6.2 资料写入

已确认：作者可手动维护；AI 只能提出更新建议，确认后写入。

建议每条提议展示目标资料、原内容、修改后内容、理由和来源。作者可接受、修改后接受或拒绝。若资料已经被修改，需重新检查差异，避免旧提议覆盖新内容。正文生成完成不自动触发人物资料写入。

## 7. 单 Agent loop：需要优先确认的产品定义

**用户已确认的是“需要 agent loop”和“第一版不做多 Agent”。本次实施采用下述有限应用动作循环，运行结束与作者审核提议分开；该采用状态不视为用户补填了需求表。**

实现方式已确认：使用 TypeScript 自行实现 Agent loop，pi-ai 负责模型供应商接入。循环调度由项目自身维护，不使用 pi-agent-core 承担循环实现。该技术决策不代表下文所有产品行为已经确认。

### 7.1 建议的循环方式

同一个 Agent 接收任务和选定 Skill，在限定范围内反复执行“请求模型 → 获取需要的资料或形成候选文本 → 接收结果 → 决定继续或结束”。它可以多轮推进一项任务，不需要建立主笔、编辑等多个独立 Agent。

本次采用应用内有限能力：检索与读取冻结的当前作品资料、使用作者选定的 Skill 内容、生成候选正文、提出修改。Skill 本身仍仅提供提示词；应用能力由程序定义，不从 Skill 中执行脚本或外部工具。协议已建立，实现在 P04/P05。

建议第一版由作者选定 Skill，不让 Agent 自行加载任意 Skill。一次任务建议面向一个片段或一章，不承诺批量生成。

### 7.2 建议的运行控制

| 事项     | 建议行为                                                       | 仍需确定的内容                         |
| -------- | -------------------------------------------------------------- | -------------------------------------- |
| 状态     | 排队、运行、等待确认、完成、失败、已取消；中断后可标为已中断   | 是否需要排队、等待确认节点             |
| 可见性   | 显示实际输入、模型响应、应用能力调用及结果                     | 展示粒度；不以展示模型隐藏推理作为要求 |
| 结束条件 | 正常完成、达到轮次上限、预算或时长阈值、作者取消、不可恢复错误 | 默认轮次、阈值及超限后行为             |
| 中止     | 作者可取消，保留已产生的候选结果                               | 是否还需要可恢复的暂停                 |
| 失败恢复 | 保留已完成轮次，从最后一个完整记录点显式重试                   | 是否支持进程重启后继续                 |
| 正文应用 | 生成结果先进入候选区，作者确认后应用                           | 是否允许每次任务选择自动应用           |
| 资料更新 | 提出更新，作者确认后写入                                       | 已确认需要人工确认                     |

失败重试建议显示已发生的用量；不默认重复提交状态不明的请求。若支持恢复，应校验已有写入，避免重复应用修改。

### 7.3 待确认后的验收目标

选择一个需要两轮以上推进的任务，能够看到每轮输入、输出与动作；正常结束或达到上限时有明确状态；错误不会丢失已保存结果；涉及资料更新时必须等待作者确认。

只完成一次模型调用，不能视为已验收 agent loop。具体动作及用例需在本节方案确认后固定。

### 9.2 建议用于首版评估的方案

同一套 Web 应用支持两种部署，数据先由部署实例持久保存。本机部署写入本机目录；服务器部署写入服务器持久卷。朋友各自部署，避免第一版引入共享工作空间和协同编辑。第一版先提供手动项目备份与恢复，跨设备自动同步后续讨论。

**本次按该方案把“本地”解释为部署实例所在机器，并据此实现 P01 的 SQLite/附件适配；浏览器离线优先和跨设备同步尚未实现。** 如改为共用服务器，需在对外可用前落实账号及作品、Skill、凭据、运行记录的访问隔离，并重评相关存储设计。

本次采用完整实例备份方向，包含作品、资料、历史版本、Skill 及其来源、测试案例和必要运行记录，排除凭据及登录会话。恢复覆盖整个实例，应检查兼容性并提供明确确认；备份格式和实现归 P07。
